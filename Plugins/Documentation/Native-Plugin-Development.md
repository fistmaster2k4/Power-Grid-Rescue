# Native Power-Grid plugin development (reconstructed SDK)

> **Status:** community reverse-engineered interface, **not** an official ROCCAT SDK. The interface and examples below have been tested with **Power-Grid 0.461**, but the full proprietary SDK has not been recovered.

## Why this exists

The original ROCCAT Power-Grid desktop application supports native Windows plugins which provide functions to JavaScript-driven controls. Its original development SDK is difficult to obtain. During the Power-Grid Rescue project we examined the original host, ROCCAT's Sample2 example, and its binaries to reconstruct a working subset of the native API.

Two real implementations now demonstrate this path:

- **[PingTest / repaired Sample2](../Plugins/PingTest/)**: restores a working asynchronous TCP connection-time check to the original example. The stock `Sample2.qs` remains in use.
- **[VREServer](../Plugins/VREServer/)**: an independently written plugin querying the public read-only server interface of Vulkan Render Engine, a C# Vulkan multiplayer survival game.

Both use the reconstructed header, compile as **32-bit Release Qt 4** DLLs, load in the original host, and provide control updates. We also verified Sample2 output updating on the Android client.

## Files and compiler prerequisites

- **[RoccatPowerGrid.h](../Development%20Tools/RoccatPowerGrid.h)**: the reconstructed minimal native interface.
- **Qt 4.8.5**, specifically the **MSVC 2010 x86** build (QtCore; add QtNetwork for networking plugins).
- **Microsoft Visual C++ 2010 SP1 x86 compiler** (compiler version **16.00.40219.01**); our verified build used **Windows SDK 7.1** and its **VC++ 2010 SP1 Compiler Update KB2519277** on Windows 7 SP1 x86.
- `qmake`, `moc`, `cl`, `link`, `nmake`, `mt` in the compiler environment.
- Compile **Release**, with the matching Qt4 release libraries; **do not distribute a debug-linked DLL** for the stock release host.

The verified environment used `C:\Qt\4.8.5`. Build output is `release\<TARGET>.dll` (e.g. `release\Sample2.dll`, `release\vreserver.dll`).

### Minimal qmake project

```qmake
QT += core
QT -= gui

TARGET = MyPlugin
TEMPLATE = lib
CONFIG += release

SOURCES += myplugin.cpp
HEADERS += myplugin.h RoccatPowerGrid.h
```

For `QTcpSocket`, `QHostAddress` and other networking APIs, use `QT += core network` and regenerate the makefile with `qmake` so **QtNetwork4.lib** is linked.

### Building

Open an x86 Windows SDK / VC++ 2010 SP1 build prompt:

```bat
call "C:\Program Files\Microsoft SDKs\Windows\v7.1\Bin\SetEnv.cmd" /x86 /release
set "PATH=C:\Qt\4.8.5\bin;%PATH%"
qmake -spec win32-msvc2010 MyPlugin.pro
nmake release
```

The Power-Grid Rescue builds also use a small bootstrap `Makefile` where `nmake release` regenerates Qt's `Makefile.Release` automatically. A raw qmake project requires the explicit `qmake` step at least once, and again whenever link settings change. The directory name is **not** the plugin version; overwriting a single working source directory is supported.

**Known standalone SDK 7.1 issue:** on some installations `intrin.h` refers to an absent `ammintrin.h`. This is a toolchain installation defect, not a Power-Grid API feature. Restore the genuine MSVC header for general development. An empty temporary stub was used *only* to get the minimal plugin through an early test and is **not a safe general SDK substitute**.

## Native Qt entry points

Power-Grid expects a normal Qt4 dynamic plugin exporting the entry points generated by:

```cpp
#include <QtPlugin>
Q_EXPORT_PLUGIN2(MyPlugin, MyPlugin)
```

The generated DLL exports `qt_plugin_instance` and `qt_plugin_query_verification_data`; its Qt4 build/verification metadata must be compatible with the host. The plugin class inherits the recovered `IFuncProvider`, supplies a `Q_OBJECT` declaration, and declares its supported interface with `Q_INTERFACES(IFuncProvider)`, allowing Qt's meta-object system to recognise it.

The interface identifier is:

```text
org.roccat.powergrid.IFuncProvider
```

**Note:** `Q_EXPORT_PLUGIN2` is the Qt4-style macro; do not silently replace it with a modern Qt5/Qt6 plugin mechanism.

## Reconstructed interface

The header defines an `IPluginBase : QObject` and `IFuncProvider : IPluginBase`. The following x86 MSVC vtable offsets were recovered from the host and original sample binary:

| Vtable slot | Declaration in reconstructed header | Purpose |
| --- | --- | --- |
| `+0x2C` | `QString GetName()` | Registers the native plugin name; must match the references in `plugin.json` |
| `+0x30` | `void SetPluginData(QVariantMap data)` | Receives a plugin-state map |
| `+0x34` | `QVariantMap GetPluginData()` | Returns a plugin-state map |
| `+0x38` | `QVariant GetValue(QString name, const QVariantList &params)` | Dispatches script calls to native functions |
| `+0x3C` | `const QStringList &GetList()` | Returns the names of supported native functions |

The two state-method **names are reconstructed placeholders**: their original spelling is unknown. Their **position and ABI-compatible signatures** are what matter. The offsets are for the tested **MSVC x86 Qt4** layout; don't assume they apply to x64 or another compiler/runtime.

### Function dispatch example

```cpp
class MyPlugin : public IFuncProvider {
    Q_OBJECT
    Q_INTERFACES(IFuncProvider)
public:
    MyPlugin() { m_functions << QLatin1String("ReadCounter"); }
    QString GetName() { return QLatin1String("MyPlugin"); }
    const QStringList &GetList() { return m_functions; }
    QVariant GetValue(QString name, const QVariantList &params) {
        Q_UNUSED(params);
        if (name == QLatin1String("ReadCounter"))
            return QVariant(42);
        return QVariant();
    }
private:
    QStringList m_functions;
};
```

Put implementation methods and the `Q_EXPORT_PLUGIN2` macro in suitable source files; add the header to `HEADERS` in your qmake project so **moc** processes it. The sample illustrates dispatch, not a full copy-paste-ready application.

**Critical lifetime rule:** `GetList()` returns a **const reference**. Return a persistent member such as `m_functions`; returning a reference to a temporary list can crash the host. One failure in the damaged original Sample2 involved this lifetime issue.

## JavaScript controls and plugin metadata

A native DLL by itself is not a complete user-facing Power-Grid plugin. The installable package also contains:

- `info.json`: package identity, author, description and the plugin-distribution flag `"Plugin":"1"`.
- `plugin.json`: native DLL name, registered plugin identity, control definitions and configurable parameters such as a host/IP or query port.
- `<Plugin>.ctrlset.json`: categorisation and control-set registration in the Power-Grid editor.
- `<Plugin>.qs`: JavaScript glue that invokes native function providers and updates controls.
- Optional art, icons, instructions and other resources.

Controls call the native provider through the established Power-Grid JavaScript bridge (e.g. `CallFunc`). The original Sample2 script invokes `SendTcpRspTime` to start a test, then `ResultTcpRspTime` to retrieve it. Power-Grid already handles moving updated control content from desktop to the phone client; new native plugins do not have to implement the mobile transport.

A proper plugin can expose **multiple functions and multiple controls**; VREServer offers 10 editor controls using a shared read-only server-query cache. Keep network I/O asynchronous, impose timeouts, and avoid blocking the Qt GUI/event loop.

## Package format: `.rpgp`

Both native-plugin installers and grid exports use ZIP-compatible `.rpgp` containers, **but are different package types**:

### Native plugin `.rpgp`

The recovered original **ExamplePlugin3.rpgp** places `info.json`, `meta.json`, `plugin.json`, `Sample2.ctrlset.json`, `Sample2.qs`, `Sample2.dll` and artwork/readme at the archive **root**. Its `info.json` contains `"Plugin":"1"`. Power-Grid recognises it as a plugin and offers an installation prompt.

### Grid export `.rpgp`

Our exported VRE grid contains `grids.json`, `controls.json`, `info.json`, and assets under `rsc/`. The grid references installed plugin control IDs such as `VREServer:ServerName` instead of bundling the required native DLL.

**Installation order:** install the plugin `.rpgp` first, then import its companion grid `.rpgp` (if supplied). A trial package that placed plugin and grid content into one root-level `.rpgp` imported the plugin but **did not offer the grid**; do not treat unified installation as supported until separately verified.

## Validation and limits

**Runtime validated:** Qt4 x86 DLL discovery, `IFuncProvider` registration, function dispatch and return values, argument passing from the editor, live desktop updates, Sample2 mobile updates, and VREServer's public VRE binary TCP query.

**Not claimed:** full coverage of ROCCAT's original SDK, compatibility with modern Qt versions without ABI adaptation, every possible control type, undocumented administrative interfaces or a fully automatic combined plugin/grid installer.

The reconstructed interface is provided for archival research and interoperability. Keep original ROCCAT attribution where appropriate; original metadata in rescued samples does not mean ROCCAT authored or endorsed our replacements.
